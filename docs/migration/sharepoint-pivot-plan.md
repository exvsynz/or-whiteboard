_Hardened plan from an Opus multi-agent workflow (12 agents; adversarially reviewed across 4 lenses, all 'ship-with-fixes'). Generated 2026-06-16. This is a planning artifact._

## Summary

Hardened final plan to migrate the OR whiteboard's PRODUCTION backend from the never-deployed/shelved Supabase layer to Microsoft SharePoint Lists via Microsoft Graph + MSAL.js (@azure/msal-browser) with Entra ID SSO, served as a static SPA. The adapter-seam thesis is verified correct (board-data.ts is a clean stateless seam; useBoard's Supabase coupling is concentrated; auth is one hook). The review surfaced real defects I have fixed; the plan is now 11 phases plus a parallel IT/Hank dependency lane. (2) Split the old monolithic P0 into P0a (data seam) / P0b (realtime+SyncIndicator) / P0c (auth seam), each separately revertible and green. (3) Corrected the demo write-path: I do NOT unify write paths — demo keeps its whole-board debouncedSave + synchronous setPeople and NEVER enters the optimistic queue; the queue stays remote-only gated on capabilities. ## Target architecture

TARGET ADAPTER ARCHITECTURE: A single BoardBackend TypeScript interface is the persistence contract; three implementations — DemoBackend (wraps board-storage.ts), SupabaseBackend (wraps board-data.ts, shelved until cutover), SharePointBackend (Microsoft Graph). Client/credentials are captured INSIDE each adapter (the `client` first-arg is dropped) so useBoard never sees a Supabase or Graph handle.

INTERFACE (anchored on backend-neutral domain types BoardPerson and AreaStatusInfo, the latter PHYSICALLY MOVED to src/lib/board-types.ts in P0a): fetchRoster(boardDate), fetchAreaStatuses(), upsertAssignment(personId, area|null, boardDate, status?), setAssignmentStatus(personId, boardDate, status), addPerson(name, role, color, boardDate)=>Promise<BoardPerson>, removePerson(personId, boardDate), replaceBoard(boardDate, people[])=>Promise<BoardPerson[]>, setAreaStatus(areaName, status, note), subscribe(boardDate, { onChange, onStatus }) => unsubscribe, writeAudit(entry), readAudit(personId), and readonly capabilities { realtime, serverGeneratedIds, serverAudit, optimisticQueue }. KEEP both granular CRUD AND whole-board replaceBoard (the optimistic queue's per-person upsert idempotency keyed on (personId,boardDate) depends on it). CONTRACT INVARIANT (locked in the shared contract test): ids returned by addPerson/replaceBoard round-trip through upsertAssignment/setAssignmentStatus/removePerson without error — catches the SharePoint item-id-shape mismatch class automatically.

CRITICAL CORRECTIONS to the draft interface, driven by the architecture lens:
- subscribe() carries BOTH onChange (refetch trigger) AND onStatus (connection state). SupabaseBackend maps SUBSCRIBED->onStatus('connected'), CHANNEL_ERROR/TIMED_OUT/CLOSED->onStatus('disconnected'), preserving the active-flag CLOSED-suppression internally. SharePointBackend drives onStatus from poll success/failure. Without onStatus the draft interface could not deliver connectionStatus to the hook (regression).
- Backend-NEUTRAL kiosk-resilience listeners (window 'online', document 'visibilitychange', the KIOSK_POLL_MS safety-net interval, refetchTimer cleanup — verified interwoven in useBoard.ts:386-404) STAY in useBoard (or a shared helper the hook always runs). Only the Supabase-specific .channel/.subscribe/.removeChannel moves into SupabaseBackend.subscribe(). This preserves wake-from-sleep / reconnect-after-blip for ALL backends including SharePoint polling.
- The optimistic write-queue is NOT unified. Verified: today flushWrite (L172 `if(!supabase) return`) and movePerson's enqueue (L482, gated on isSupabaseConfigured) never run in demo; demo persists via the whole-board debouncedSave effect (L410-418) + synchronous setPeople. The queue stays REMOTE-ONLY, gated on backend.capabilities.optimisticQueue. DemoBackend.upsertAssignment is a no-op for persistence (the debouncedSave effect owns demo persistence). Rule preserved and grep-asserted: demo never enters flushWrite/enqueueWrite.
- The THREE async-shape-divergent actions keep their demo-vs-remote branch even after P0: addPerson (sync setPeople + crypto.randomUUID in demo L512-526 vs async DB-id adoption in remote L491-510), resetBoard (sync setPeople(DEMO_PEOPLE) vs await replaceBoard([])), importPeople (identity in demo vs await replaceBoard). Only the genuinely symmetric actions (movePerson optimistic UI, setPersonStatus, area-status) de-branch. This honors the byte-for-byte demo constraint (the synchronous addPerson test asserts the card in a single act()).
- Demo audit (actionType derivation + logAuditEntry) STAYS in useBoard (it has fromArea/toArea in hand), gated on `!backend.capabilities.serverAudit` (not on isSupabaseConfigured). SupabaseBackend.writeAudit is a no-op (serverAudit:true — the DB trigger owns it; calling it would double-log). DemoBackend.writeAudit wraps the in-memory audit-client (serverAudit:false). SharePointBackend.writeAudit POSTs (serverAudit:false). SupabaseBackend.readAudit must port useAuditLog.ts:41-69 verbatim incl. the getAreaMaps UUID->name join (so HistoryDrawer shows names, not UUIDs).
- AuthAdapter produces the SAME UseAuthReturn from either Supabase session or an MSAL account; login(email,password) widens to login(email?,password?) with args ignored by MSAL.
- Mode selector models FOUR states, not a naive enum: resolve a concrete backend if its env is fully present; else if DEMO_MODE=>demo; else => a 'misconfigured' sentinel carrying WHICH backend was half-configured (so AuthGuard names the right missing vars). Preserves the verified orthogonal isSupabaseConfigured/isDemoMode flags and AuthGuard's three-state UI (demo bypass / misconfig panel / login).
- The SharePoint adapter module and msal-config are loaded via DYNAMIC import (await import) behind the runtime mode check, so a static getBoardBackend() factory does not pull @azure/msal-browser into the demo bundle or jsdom tests.

HOSTING + AUTH DECISION (recommended, pending IT): Azure Static Web Apps host at the root path + MSAL.js auth-code+PKCE delegated SSO; Entra app registered with a 'Single-page application' platform (NOT 'Web'; implicit grant OFF). Near-realtime defaults to the EXISTING 60s full-GET poll on the indexed BoardDate column (delta query is a deferred optimization, not v1 — verified the existing poll is trivially within Graph throttling budget for a single-suite ~60-120-row board). RBAC moves from Supabase RLS to SharePoint list permission levels mapped to Entra security groups (viewer=read, editor=contribute), set AT LIST CREATION — client isEditor is cosmetic; a viewer's delegated Graph token must be denied write at the list level or every authenticated user can mutate the board (the RLS safety net never deployed). Role claim source = App Roles (idTokenClaims.roles), defined in the app manifest at P-IT registration time — avoids the >200-group claim-overage problem and needs no extra Graph scope.

GRAPH SCOPE: delegated Sites.Selected with a SITE-LEVEL write grant (POST /sites/{id}/permissions roles:['write']) on a DEDICATED whiteboard site — the documented happy path for the listItem delta endpoint and simpler to administer; the dedicated site bounds the blast radius. NOTE the verified platform risk: listItem:delta documents only Sites.Read.All/Sites.ReadWrite.All as delegated scopes, NOT Sites.Selected — so v1 deliberately uses a plain $filter GET poll (works under Sites.Selected), and delta is adopted only if the P-SPIKE/P3 spike empirically confirms delta works under Sites.Selected on the dev tenant; otherwise we either negotiate Sites.Read.All with IT or stay on the $filter poll. List-level grants (Lists.SelectedOperations.Selected) are rejected for v1: they break inheritance, count against unique-permission-scope limits, and may not support delta at all.

KIOSK AUTH (the real #1 blocker): MSAL silent refresh hinges on a ~24h refresh token; Conditional Access (sign-in frequency, persistent-session-off, CAE revocation, compliant-device) will log out an unattended wall display with no human to complete MFA. Resolution is a HARD P-IT decision + a P1 EXIT GATE that leaves a dev-tenant kiosk account signed in >24h (or applies a short CA sign-in-frequency to the test account) and confirms unattended recovery. If it cannot stay authenticated unattended, the architecture is NOT serverless and an Azure Function token-broker (app-only + certificate, since a cert cannot live in a browser SPA) becomes an explicit added phase — surfaced NOW, not at cutover. Cache location is tied to this decision: a dedicated single-purpose kiosk account favors localStorage (survives restart, enables silent SSO on reboot); a genuinely user-shared device keeps sessionStorage and accepts interactive re-login per session.

STATIC EXPORT: Next is 16.2.6 (a real published release, verified — NOT a private fork; the AGENTS.md banner is generic Next-16-breaking-changes boilerplate). node_modules/next/dist/docs documents output:'export' and a working out/ already exists. So 'can it export' is a one-line sanity check post-refactor, NOT a phase-blocking risk, and the 'SPFx forced if export breaks' escalation is removed. SPFx remains only the fallback if hospital IT forbids any non-SharePoint host (it forces a React 19->17 rewrite + AadHttpClient — strictly costlier). This app has exactly ONE route ('/'), so the SPA-deep-link-404 concern is largely moot; navigationFallback to /index.html is kept only as cheap insurance for the MSAL redirect return, with /config.json excluded from the fallback so a missing config 404s loudly instead of returning HTML-as-JSON.

- **[nit]** Runtime config.json fetch on a static SPA needs its own SPA-fallback / caching consideration and a demo-mode guard (phase P5)
  - The plan's runtime-config-injection idea (config.json fetch / window.__ENV) is the right call for IT-redeployable bundles, but a few edges: (a) on Azure Static Web Apps the navigationFallback to /index.html (P5) can accidentally return index.html for a mistyped /config.json path, yielding HTML-parsed-as-JSON instead of a clean 404 — the fallback must exclude the config path; (b) the kiosk caching a stale config.json across a tenant/clientId change could cause silent auth failure; (c) demo mode (NEXT_PUBLIC_DEMO_MODE=true, the test/default path) must NOT attempt the fetch or it adds a startup network call into jsdom tests that currently have no global mock.
  - Fix: In staticwebapp.config.json, exclude /config.json from navigationFallback (so a missing config 404s loudly instead of returning index.html). Set cache-control: no-cache on config.json. Guard the config fetch so it is skipped entirely in demo mode and returns a static default — keeping the jsdom test path network-free (consistent with the 'no global Graph mock in setup.ts' constraint).
